# Original frontend and ending integration

Reference: owner-supplied `v0.111.0 / 41cef1ea`, single-player. The relevant original behaviors are `NMainMenu.RefreshButtons`, `NMainMenu.AbandonRun`, `NPauseMenu`, `NAbandonRunConfirmPopup`, `RunManager.AbandonInternal` and `NFastModeTickbox`. Only resource keys and numeric layout metadata are committed; the source game and converted images remain private inputs.

## Menus and storage

`frontend_input.inc` separates menu presentation from the saved simulation. A validated unfinished save exposes Continue and Abandon; otherwise the first entry is Single Player. Compendium, Settings and Quit follow. Save metadata is decoded into a single aggregate-initialized static scratch State, so inspection cannot overwrite the visible run or consume its RNG. Continue validates the complete candidate and its unfinished phase before assigning it. Rejected or corrupt loads leave the visible state unchanged. Successful probes, loads and saves all use one metadata update path; Continue therefore remembers the newly loaded file even if it changed after the menu was drawn.

The pause menu uses the five original single-player actions. Save and Quit writes successfully before returning to the main menu; a failed save keeps the pause menu open. Give Up asks for confirmation and uses the core's forced player death with its actual continuations. The title's Abandon removes the saved expedition after confirmation. These are gameplay dialogs, not development approval requests.

`Callbacks::clear_save` is optional for test/embedded hosts. The production X11 host deletes its save; Ndless removes backup and temporary files before its main save; the paired browser host interprets the explicit `save(nullptr, 0)` call as deletion of all known v3–v15 local-storage keys. Ordinary serialized saves are nonempty. This prevents an old browser fallback key from reviving an abandoned run. Without deletion, Give Up first forces death on the scratch copy and saves that terminal state. Only a successful write replaces the visible game with the copy. A failed write keeps the real game, its RNG, death-prevention items and pause screen intact. Title abandonment applies the same terminal-write fallback to the freshly read saved run and never assigns it to the unrelated visible game.

End-of-run cleanup first distinguishes the bootstrap seed, character, native-world mode and practice mode. Native runs additionally compare the complete 64-bit original run seed, ascension and initial region in `world.rooms[0]`. The current act's region is not the initial region. Named-seed initialization in a historical legacy run does not make it a native run. A different identity leaves the saved expedition intact.

Matching parameters are insufficient authorization to delete a checkpoint. App separately retains the complete checkpoint fingerprint from the current run's most recent successful save or Continue. A newly started run clears this association, even when all its parameters happen to match another saved run. Cleanup rereads the file and requires its fingerprint to match the associated checkpoint. An imported or cross-host same-parameter run without that association is conservatively refused; explicitly continuing the file establishes the association. Merely inspecting the menu does not.

The title's Abandon dialog similarly requires a successful fresh read when it opens, records that exact fingerprint, and rereads before accepting. Replacement with a different run or different progress under the same parameters requires a new confirmation. An unreadable or invalid expected checkpoint never becomes permission to delete it or to kill the visible player. The last known checkpoint evidence survives a failed menu refresh, although Continue is hidden until another successful read.

Fingerprints are 64-bit FNV-1a plus encoded length over the entire canonical save, including all saved fields; C++ structure padding is excluded. A second aggregate-initialized static `SaveData` workspace avoids placing the 262,144-byte buffer on the calculator's stack. The fingerprints and metadata exist only in App, with no new State fields or encoded bytes. They detect ordinary file replacement, not adversarial collisions, a global run UUID or an atomic compare-and-swap operation. The current callback contract cannot prevent a separate writer racing between the final read and removal/write. Its boolean `load` result also cannot distinguish an absent file from an initial I/O failure: known or associated checkpoint failures are refused, while a never-saved run with no observed checkpoint can still be abandoned. Hosts must report writes/deletions truthfully and supply their own atomicity guarantees.

Settings currently provides presentation speed and the calculator's control reference. The title additionally exposes practice and the reference-map tool there. The speed switch changes only UI animation advancement, with no game-state, save or RNG change. Settings are retained for this application session. Audio, desktop video options, remappable controls and persistent cross-run preferences are not implemented by this screen.

## Drawing and interaction

`native_controls.inc` draws the original back, confirm and proceed components and their original icon/outline layers. Authored transparent margins and bitmap aspect ratios are retained; callers provide readable hit rectangles for the 320×240 display. Character selection uses its original fuzzy information panel and gold highlight behind a 27×40 portrait; the corresponding highlight is 33×47. Continue's original nine-patch panel shows only facts available in the save. It does not fabricate a last-saved timestamp.

`world_game_over_ui.inc` gives completed and defeated native expeditions their original Continue → summary → main-menu sequence. It uses the pinned build's completion banner and stable initial defeat banner without consuming a game RNG draw. The summary resolves original floor/ascension text and shows current HP, gold, deck, relics and seed. Gold balance is never substituted for cumulative gold gained. Score, run duration, badges, unlocks and exact kill attribution require history that the present save does not contain.

Frontend confirmation, settings and summary selection are App-only fields. Modal input guards prevent underlying game-over actions from firing, and pointer context changes invalidate captured gestures. The existing deck and relic inspectors remain available from the summary. The original full character death animation, cross-run progress and repeat-history presentation remain separate unfinished work.

## Verification boundaries

Regression sources cover menu visibility, atomic rejected loads, real save/clear failures, forced abandonment, native seed/ascension/first-region identity, unassociated same-parameter saves, progress-only replacements during title confirmation and terminal cleanup, refreshed Continue metadata, transient reread failure and the active/title/terminal fallback-write paths. Every rejected-operation case compares the complete canonical visible state and retained disk bytes. Modal exclusivity, original ending branches and presentation-only settings remain covered. Both frontend/ending UI suites accept an actual private pack and optional screenshot directory. Synthetic profiles test interaction and bounds; they do not establish visual fidelity. Native/WASM frame agreement establishes this project's backend consistency and is not an original-game screenshot oracle. No 95% similarity score is claimed.
