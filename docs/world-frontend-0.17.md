# Original frontend and ending integration

Reference: owner-supplied `v0.111.0 / 41cef1ea`, single-player. The relevant original behaviors are `NMainMenu.RefreshButtons`, `NMainMenu.AbandonRun`, `NPauseMenu`, `NAbandonRunConfirmPopup`, `RunManager.AbandonInternal` and `NFastModeTickbox`. Only resource keys and numeric layout metadata are committed; the source game and converted images remain private inputs.

## Menus and storage

`frontend_input.inc` separates menu presentation from the saved simulation. A validated unfinished save exposes Continue and Abandon; otherwise the first entry is Single Player. Settings, Compendium and Quit follow, matching the original menu order after the excluded multiplayer and Timeline entries are removed. Save metadata is decoded into a single aggregate-initialized static scratch State, so inspection cannot overwrite the visible run or consume its RNG. Continue validates the complete candidate and its unfinished phase before assigning it. Rejected or corrupt loads leave the visible state unchanged. Successful probes, loads and saves all use one metadata update path; Continue therefore remembers the newly loaded file even if it changed after the menu was drawn.

The pause menu uses the five original single-player actions. Save and Quit writes successfully before returning to the main menu; a failed save keeps the pause menu open. Give Up asks for confirmation and uses the core's forced player death with its actual continuations. The title's Abandon removes the saved expedition after confirmation. These are gameplay dialogs, not development approval requests.

`Callbacks::clear_save` is optional for test/embedded hosts. The production X11 host deletes its save; Ndless removes backup and temporary files before its main save; the paired browser host interprets the explicit `save(nullptr, 0)` call as deletion of all known v3–v15 local-storage keys. Ordinary serialized saves are nonempty. This prevents an old browser fallback key from reviving an abandoned run. Without deletion, Give Up first forces death on the scratch copy and saves that terminal state. Only a successful write replaces the visible game with the copy. A failed write keeps the real game, its RNG, death-prevention items and pause screen intact. Title abandonment applies the same terminal-write fallback to the freshly read saved run and never assigns it to the unrelated visible game.

End-of-run cleanup first distinguishes the bootstrap seed, character, native-world mode and practice mode. Native runs additionally compare the complete 64-bit original run seed, ascension and initial region in `world.rooms[0]`. The current act's region is not the initial region. Named-seed initialization in a historical legacy run does not make it a native run. A different identity leaves the saved expedition intact.

Only a successful save or Continue associates the visible run with the host's save. Starting a new run clears that association, even when its parameters happen to match another saved run. Finishing an unassociated run therefore leaves that file alone without reading or deleting it. Associated cleanup rereads once and checks the necessary run identity; normal HP, gold or other progress changes do not make the run a different expedition. A true read, write or deletion failure leaves the operation retryable.

The title's Abandon dialog requires a successful fresh read when it opens and records the compact run identity. It rereads before accepting; replacement with a different run requires a new confirmation. Ordinary progress under the same parameters remains the selected run. Successful deletion does not issue another redundant read. Failed menu refreshes hide Continue but preserve the visible run's existing save association.

The frontend no longer encodes a second complete save, computes FNV over it, or retains a content fingerprint. Removing the duplicate `SaveData` workspace saves 262,144 bytes of static storage and removes the extra encoding/scan from each probe and save. The host still performs its functional load or write. The boolean callback contract is unchanged and does not provide an atomic compare-and-swap or a global run UUID; the presentation does not invent either mechanism.

Settings currently provides presentation speed and the calculator's control reference. The title additionally exposes practice and the reference-map tool there. The speed switch changes only UI animation advancement, with no game-state, save or RNG change. Settings are retained for this application session. Audio, desktop video options, remappable controls and persistent cross-run preferences are not implemented by this screen.

## Drawing and interaction

The original `scenes/backgrounds/main_menu_bg.tscn` places `main_menu_logo` as a SpineSprite at `BgContainer/Control/Logo`. The historical converter incorrectly chose the separate white-outline `sts2_logo_static.png`. `tools/title_assets.py` now follows the source Control anchors and CanvasItem transforms, then applies the same cover crop to the 320×240 display. `config/title-scene-0.17.json` records the source and geometry; no original artwork is committed.

The source logo has one static text attachment and ten small fire attachments repeating every second. Image 4 is replaced by a 164×106 atlas: one 164×84 text region and ten 16×22 flame regions. Runtime selects a flame every 100 ms without copying the letters or adding a clip. Its sparse raw payload is 32,274 bytes for the pinned original source. Historical packs with the old image dimensions keep their static rendering path. The independent `light_large` glow and background particle systems are not yet reproduced.

The menu is centered beneath the original logo at x=119 with 20-pixel rows, readable fitted labels and the original left/right highlight texture. The right highlight mirrors the existing image. A 174-pixel hit width keeps menu actions outside the Continue panel. The panel uses the original character icon and shows character, floor, ascension, HP and gold. Its labels use original localization keys, and it does not fabricate a last-saved timestamp.

`native_controls.inc` draws the original back, confirm and proceed components and their original icon/outline layers. Authored transparent margins and bitmap aspect ratios are retained; callers provide readable hit rectangles for the 320×240 display. Character selection uses its original fuzzy information panel and gold highlight behind a 27×40 portrait; the corresponding highlight is 33×47. Continue's original panel shows only facts available in the save.

`world_game_over_ui.inc` gives completed and defeated native expeditions their original Continue → summary → main-menu sequence. It uses the pinned build's completion banner and stable initial defeat banner without consuming a game RNG draw. The summary resolves original floor/ascension text and shows current HP, gold, deck, relics and seed. Gold balance is never substituted for cumulative gold gained. Score, run duration, badges, unlocks and exact kill attribution require history that the present save does not contain.

Frontend confirmation, settings and summary selection are App-only fields. Modal input guards prevent underlying game-over actions from firing, and pointer context changes invalidate captured gestures. The existing deck and relic inspectors remain available from the summary. The original full character death animation, cross-run progress and repeat-history presentation remain separate unfinished work.

## Verification boundaries

Regression sources cover menu visibility, atomic rejected loads, real save/clear failures, forced abandonment, native seed/ascension/first-region identity, unassociated same-parameter saves, ordinary progress during title confirmation and terminal cleanup, refreshed Continue metadata, transient reread failure and the active/title/terminal fallback-write paths. Every rejected-operation case compares the complete canonical visible state and retained disk bytes. Modal exclusivity, original ending branches and presentation-only settings remain covered. Both frontend/ending UI suites accept an actual private pack and optional screenshot directory. Synthetic profiles test interaction and bounds; they do not establish visual fidelity. Native/WASM frame agreement establishes this project's backend consistency and is not an original-game screenshot oracle. No 95% similarity score is claimed.

The title regression checks that only the flame rectangle changes across its ten frames, the complete frame repeats after one second, and animation leaves the saved simulation unchanged. Canvas region tests use an independent destination-to-source oracle for raw, indexed, alpha and sparse images, including mirrors, source/target clipping, row pitch, coverage and blend parameters. The room-layer fixture samples the lower-right actor plane above the original Proceed arrow, so it still checks the exact composite color without treating a correctly overlaid button as a background defect. These are implementation regressions, not original-game visual acceptance.
